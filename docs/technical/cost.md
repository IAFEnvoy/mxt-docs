# 消耗

所有"要付什么"的字段都是一份消耗数组，技能、修炼、阵法、锻造、契约、符箓、品质升级共用这一种形状。真正把它付掉的是 `CostPayment`（一块**账单**），而每一项消耗自己只做一件事：给出**已经绑定好的事务**。

| 层 | 名字 | 负责 |
| --- | --- | --- |
| 定义 | `Cost`（`mxt:resource` / `mxt:aura` / `mxt:item` / `mxt:js`） | 把上下文算成一份事务：金额求值**一次**、存储从上下文解析、参数就地冻结 |
| 绑定后的费用 | `Cost.Transaction` | 固定目标 `CostTarget` + 固定数量 `amount`，只有 `execute(simulate)` 两个状态 |
| 账单 | `CostPayment` | 报价、改价、统一模拟、统一实扣、累计真实凭据 |

写这个形状的目标只有一个：**这一笔到底多少钱、扣了没有、扣了多少，永远只有一个答案。**

## 一次付款的四步

| 步骤 | 入口 | 写不写 |
| --- | --- | --- |
| 报价 | `CostPayment#price(costs)` / `price(costs, context)` | 不写。只调每个条目的 `prepare(context)`，返回事务 |
| 改价 | `replaceResourceAmounts(表)` / `scale(选中, 比例)` | 不写。把选中的费用换成**新的事务**（同一个绑定、新的固定数量） |
| 检查 | `CostPayment#test()` | 不写。按目标合并后逐组 `execute(true)` |
| 付款 | `CostPayment#pay()` | 写。先逐组模拟一遍，全部通过后再逐组 `execute(false)` |

`pay(costs, ctx)` 是"报价 + 付款"两条命令合一，静态入口与 KubeJS 的单条消耗都走它，没有第二条更快的路。

报价与改价是**准备**，检查与付款是**执行**：`pay()` 之后账单封闭（`closed`），再报价、再改价、再 `pay` 都只会拿到同一个终态，不会扣第二次。`price` 之后直接 `pay` 也仍然会跑完整的模拟——"检查过了"不是一张通票。

## 为什么金额在报价时就绑死

旧写法的第一层是"两遍调用同一个方法"：`execute(context, true)` 算金额并写进付款的共享价格表，`execute(context, false)` 再按自己那一份读回来。它的钱有两个来源——条目自己的公式，以及付款那张表——为了让这两份对上，它需要一张份额表、一次比例反推，还要一个"现在是在验证还是在实扣"的标志位。

| | 两遍调用同一个方法 | 报价返回绑定事务 |
| --- | --- | --- |
| 金额谁定 | 模拟那一遍写进表，实扣那一遍按份额读回 | `prepare` 求值一次，之后不再读公式 |
| 动态公式 | 每遍各求一次，可能给出两个价 | 只求一次，实扣用的就是报价那个数 |
| 改价 | 改表，再按份额反推每项该出多少 | 换成一个新事务，金额就是新金额 |
| 只报价不付款 | 需要一个跨阶段的标志，否则脚本实扣会被跳过 | 没有标志，`pay` 自己总会跑两遍 |
| 一个目标两项 | 必须摊派，否则同一个余额被查两次扣两次 | 账单在冻结时相加，只扣一次 |

份额那套的代价是**它自己会出错**，而且出错的方式都不显眼——账单改过之后，条目按比例反推出来的数可以和改价后的总额不一致。

## 为什么一个存储只该写一项

同一份余额被两项写到，两遍执行就变成"同一个余额被查两次、扣两次"。旧设计选择容忍它、再摊派，这套宽容直接带出四类会扣错钱的缺陷：

1. **金额对不上**。一项按公式、一项按份额，改价之后两者不一致：删掉的价格仍按原价扣，新加的价格又没有对应的执行条目。
2. **拒付仍然写了一半**。查的是"这一项够不够"，写的时候按自己那一份写；第二项拒绝时第一项已经扣掉。物品条目尤其明显——边找边扣，材料不足会先把现有材料扣光再报失败。
3. **凭据与实际扣除不符**。扣空之后才去复制凭据，拿到的是空堆；银行只给出部分、仍然报成功。
4. **重入与终态失守**。一个目标被两条路径碰到时，同一次付款里再进入一次不会触发守卫；脚本条目每次报价都生成新目标，嵌套付款因此绕过守卫。

四类问题的共同点不是"多扣了一点"，而是**这一笔到底多少钱、扣了没有、扣了多少变成了三个可能互相矛盾的答案**。所以现在不做摊派：

- 账单冻结时按 `CostTarget` 分组，同一个目标的金额在**那个存储自己的单位**里相加，用一个事务扣一次；
- 目标身份是物理的，不看消耗类型：`mxt:aura` 在付款者身上扣的是它度量的那个数值，所以它和写那个数值的 `mxt:resource` 是同一个目标；池、银行、账户即使装的是同一门灵气也各是各的目标；
- 相加只对"纯数值"成立：物品按容器 + 匹配项分组，脚本永远不合并（脚本拿多少是它自己的业务，不是一个可以相加的数）；
- 写重了**不是加载错误**，账单会打一条运行期警告然后照常算对——但读这段代码的人得自己把两项加起来，所以形状要求仍然是[一项一个目标](/datapack/types/shared_data_types#cost)。

## 两种被放弃的写法

**草稿 + 快照回滚。** 曾经每个条目在付款构造时被拷一份草稿，失败就把真正写下的部分还原。它的问题是跨通道根本回滚不了：共享灵气池被别的系统掏空、脚本已经 consume、物品已经进了别的容器，这些都没有"放回去"的操作；为了看起来能回滚，它还得记住"哪些写成功了"，而这本身就是又一份要与真实状态对齐的账。现在的取舍是：**内置单条全有或全无，整组先模拟，实扣失败不误报也不重试，已扣的部分如实返回**（`PaymentResult` 带上真实凭据）。

**多笔付款依次提交。** 修炼曾经把它拆成"环境灵气一笔 + 身体费用一笔"，再依次提交。两笔之间没有任何边界，第二笔失败时第一笔已经扣掉。现在不同上下文的费用可以并进**同一块账单**（`price(costs, context)` 换个上下文），模拟与实扣都在一次付款里做完。

## 每种存储的实扣

| 目标 | 模拟 | 实扣 | 单位 |
| --- | --- | --- | --- |
| 数值账户（`CostTarget.Account`） | `tryConsume` 跑在一份副本上 | `tryConsume` | 实数，必须有限且为正 |
| 世界灵气池（`CostTarget.AuraStore`，键是区块 section） | `canConsume` | `AuraService.consume`，全有或全无 | 实数 |
| 方块实体存量（`CostTarget.AuraStore`，键是那个方块） | `extract(…, true)` | 再问一次 `extract`，剩余量不为 0 就按拒付 | 整数，报价时向上取整一次 |
| 容器（`CostTarget.Items`） | 只读规划槽位 | 复核后集中写入，凭据是真正离开的堆副本 | 整数，报价时向上取整一次 |
| 脚本（`CostTarget.Script`） | `check` | 再 `check` 一次，然后 `consume` | 一次调用，凭据记 1 |

物品这一段值得单独看：规划阶段只读，把"哪个槽位出几个"排成一张表；写入前再复核一遍槽位与数量，然后才 `shrink` 并通知容器。这样单条物品需求是全有或全无的，不会出现"材料不够但先扣光"的中间态。

执行顺序由账单决定，不交给调用方：内置存储先跑，脚本最后，同一类里保持书写顺序。脚本在实扣之前会再问一次条件，所以单个事务被单独执行时也绕不过它自己的检查。

## 代价与限制

- **整组不回滚。** 实扣第二组时被拒，第一组已经扣掉的保留，结果里如实带上这部分凭据。防守放在数据形状上（一个目标一项），不放在回滚上。
- **写入之后抛异常不进入终态。** 库外实现或脚本在写完之后抛异常时，这次付款没有终态可缓存，它**不保证**下次不会重复扣——调用方要么自己兜住异常，要么不要在中途抛。
- **同一容器里的多条不同匹配项各自全或无。** 它们不是一份共享的最优装槽计划：两条接受不同物品的需求各自检查、各自写入，第二组可能因为第一组已经吃掉库存而失败。包作者应当避免重叠需求。
- **脚本是黑盒。** 不参与金额合并、不能部分执行，`consume` 之后也无法自动退款；脚本必须自己对重复调用保持幂等。
- **外部银行只有"物流"语义。** `extract` 返回的是没能取走的剩余量，不是"要么全给要么不改"，所以银行条目以"剩余量为 0"作为付清，部分转移按拒付处理，也不会把已经转移的那部分塞回去。
