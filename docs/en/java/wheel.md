# Wheel Entries

Abilities, spirit power and artifact skills share one **twelve-sector wheel**, and it is the **only** way any of them is triggered; the two client hotbars - and their separate configuration screens - have been deleted. The framework lives in `com.iafenvoy.mxt.screen.wheel`, the contents in `com.iafenvoy.mxt.screen.wheel.content`. The wheel is a **main wheel plus pages read from what you carry**, strung together by **one continuous cell numbering**: the main wheel is the twelve cells you arrange (numbers `0..11`), the pages behind it (main hand / off hand / artifacts) come from your gear and are numbered from `12` on, numpad `4` / `6` turn the pages, and `R` always opens the main one (see [The main wheel, the pages behind it, and cell numbers](#the-main-wheel-the-pages-behind-it-and-cell-numbers)).

**The framework does not decide what is on the wheel.** `WheelMenuProvider` answers "what does this source contribute right now" (`entries(player, source)`, where `source` is a `WheelSource`; the answer **may be longer than one page**, and the framework pages it), and its only implementation is `WheelContent` (registered from client setup by `WheelContent.register()`). `WheelMenuEntry` is the entry contract:

| Member | Meaning |
|---|---|
| `WheelEntryKind kind()` | `ABILITY`, `AURA` or `ARTIFACT`: the tooltip's first line, the pool it appears in, and which side of the server dispatch triggers it. |
| `Identifier id()` | The definition's id (an entry of `mxt:ability` or `mxt:aura`); `ARTIFACT` uses the **artifact's id plus the capability's key** (`ns:path/key`), see [Artifact skills](#artifact-skills). |
| `Component title()` | The name **drawn in the middle of the wheel**. |
| `Optional<IconReference> icon()` | The icon drawn inside the sector; a texture or an item, and optional (an artifact skill draws its name instead). |
| `int accentColor()` | The strip along the bottom of the cell in the editor (spirit power blue, ability gold, an artifact skill green, grey or violet by its state). |
| `List<Component> tooltip(Player)` | Kind, name and the numbers the definition carries; rebuilt on demand, because those numbers depend on the player right now. |
| `long cooldownTicks(Player)` / `boolean usable(Player)` | Ticks left, `0` meaning ready; an unusable entry dims its sector and says "On cooldown 4.3s" in the middle. It deliberately does **not** stop the trigger from being sent - whether it may be used is the server's call. |
| `void onSelected(WheelSelection)` | The trigger callback (the use key or a left click); the wheel **stays open** across it, so an implementation may open a screen of its own and may be called again for another cell. The `WheelSelection` carries the cell's number and the source it was read from. |

```java
public record AbilityWheelEntry(Identifier id, Ability definition) implements WheelMenuEntry {
    @Override public WheelEntryKind kind() { return WheelEntryKind.ABILITY; }
    @Override public Component title() { return DefinitionText.name(this.id, "ability"); }
    @Override public Optional<IconReference> icon() { return this.definition.icon(); }
    @Override public void onSelected(WheelSelection selection) { WheelTrigger.send(this, selection.source()); }
}
```

## The main wheel, the pages behind it, and cell numbers

The wheel is a **main wheel plus pages read from what you carry**, strung together by **one continuous cell numbering**. The source of a page is `runtime/wheel/WheelSource` (an enum, and its order is the numbering order):

| `WheelSource` | Name | Where its contents come from | Stored? |
|---|---|---|---|
| `CONFIGURED` | Main wheel | The twelve cells the player arranged, in the `wheel_layout` attachment | Yes |
| `MAIN_HAND` | Main hand | The active abilities the main-hand item **grants** right now, plus the **skills** that item declares as an artifact | No, read live |
| `OFF_HAND` | Off hand | The active abilities the off-hand item grants right now, plus the skills it declares | No, read live |
| `CURIOS` | Artifacts | The active abilities the equipped Curios items grant right now, plus the skills those artifacts declare | No, read live |

- **Cells are numbered straight through the whole wheel**: the main wheel is `0..11`, and the cells read from what you carry follow from `12` on.
- **A page is twelve cells**: each source takes `ceil(entries / 12)` pages, and **none at all while it holds nothing** (the main wheel always takes its one). So "one secondary wheel is not enough, open another": fifteen abilities take two pages - three cells on the second and nine empty ones - and **nothing is dropped**.
- Pages come and go with the gear, **so the numbers behind them shift**. A number is a place ("which cell"), not an identity - which is exactly what is wanted: putting an item away leaves the number alone, and taking it out again points the same number at the same skill.
- The page list only exists on the client (`screen/wheel/WheelMenuContent#pages`, one `WheelPage` each); the server never learns how many pages there are.

A derived source reads the **ability grant ledger** (the `SourceLedger` inside `AbilityAttachment`), which was already counted by source (an equipment slot records `mxt:equipment/<slot>/<item>`, Curios records `mxt:curios_equipment`); the way those ids are written lives in `runtime/ability/AbilitySources`, shared by the granting side and the wheel. Reading and deciding both live in `runtime/wheel/WheelSources`: `abilities(entity, source)` is everything one source contributes right now (active abilities only, in id order, **never cut short** - paging is the client's business), `equipment(entity, source)` is the stacks that page reads (both hands plus Curios for the main wheel, see [Artifact skills](#artifact-skills)), `toggles(entity, source)` reads the **artifact skills** off those stacks, and `offers(entity, source, kind, id)` answers "does this source still hold this entry". **Nothing about a derived source is stored**: swap the item or take the artifact off and those pages are gone in the same breath - a skill too, since it is read off the stack rather than off the ledger.

`R` opens the wheel when **any cell of any page holds anything**, so an empty main wheel cannot hide the pages behind it.

## Artifact skills

The rule is one sentence: **everything a player has to press for counts as a skill and goes on the wheel**. Every entry of an artifact's `abilities` list that implements `ToggableArtifactAbility` is such a thing - implementing the interface is the whole of saying "put me on the wheel" (the design is in `research/32_法器开关与轮盘接线设计.md`). That covers a **switch** (`mxt:flight`: on takes off, off lands) and a **one-shot** (`mxt:storage`: the press opens the artifact's own storage box and leaves nothing behind) alike. The interface leaves four questions to the implementation:

| Method | Who asks it, and what for |
|---|---|
| `String key()` | The capability's name inside its artifact, unique within one definition (`flight` / `storage`). **A wheel cell is identified by the artifact's id plus this key.** |
| `Component displayName()` | What the cell is called (`wheel.mxt.artifact_skill.flight` / `.storage`). |
| `Optional<Boolean> state(ArtifactToggleContext)` | Whether there is an on/off state at all and which side it is on; **empty means a one-shot** (the storage is). **Both sides ask**: the client draws it, the server decides from it. |
| `Result activate(ArtifactToggleContext)` | The key was pressed, answering "did anything happen, and why not" (`Failure`: not carried / not yours / already in that state / cannot be used now). Server only. |

The rules that follow:

- **Identity is the artifact's id plus the key**, written `ns:path/key` and built and parsed by `ArtifactCapability`, so **an artifact may declare several skills, one per key** - the same sword can fly and hold things; the same key twice is refused when the definition loads. `WheelEntryKind.ARTIFACT.exists` requires that pair to really exist, so a submitted layout cannot smuggle in a bare artifact id.
- **The state belongs to the implementation**, not to a data-pack field: flight reads the player's own `FlightAttachment`, the storage has none. The cell is a **report** of it - a switch is green while it is on, grey while it is off, a one-shot is violet (`ArtifactWheelEntry`) - with a tooltip saying "Artifact: X" and, when there is one, "State: on / off"; `usable` follows `ArtifactService#mayUse` so an artifact that is not yours is drawn dim. **The cell draws the capability's name rather than the artifact's item**: two skills of one artifact would otherwise be two identical sword icons, and the tooltip is where the artifact is named.
- **It appears on the page whose equipment declares it** (after the abilities, in id order) and in the editor's right-hand pool, so it can also be pinned to any main-wheel cell. Those twelve cells store the `artifact/key` pair, so a pinned cell reads **both hands plus Curios** (a backpack is not "on you") - the same stacks a derived page reads.
- **Pressing it only says "this cell was pressed"**: the request carries no direction and no action, and the server asks the implementation (see [Triggering](#triggering)). That is not how the `enabled`-carrying `FlightToggleC2SPayload` works, and that channel has no client sender today.
- **The storage cell opens a vanilla chest menu**: `MxtMenus.ARTIFACT_STORAGE` registers a plain `ChestMenu` (with the row count in the `IMenuTypeExtension` data) and the client registers the vanilla `ContainerScreen`, so **the window has no menu class and no screen class of its own**. Its container is `runtime/artifact/ArtifactStorageContainer`, a live view that reads the artifact's component and writes the whole contents back on every change; it deliberately **holds no stack**, so the moment the artifact leaves the player `stillValid` is false and the per-tick menu check closes the window. Slot count comes from the definition: **rounded up to whole rows of nine, at most six rows = 54 slots**, so capacity and window are always the same number.

## Where the twelve cells come from

1. **The player's own layout**: the `wheel_layout` player attachment (`WheelLayoutAttachment`) holds one twelve-cell `WheelLayout`; each cell is a `WheelSlot` (a `WheelEntryKind` plus an id) and an empty one uses the `WheelSlot.EMPTY` sentinel. The same attachment carries an `armed` field - **the number of the chosen cell** (an `int`, see [Keeping the selection](#keeping-the-selection)). The attachment syncs to its owner. **Only the main wheel is in it**; the pages behind it are not stored.
2. **The editor** (`WheelConfigurationScreen`) edits that layout: six columns of spirit power and six of "abilities and artifact skills", each scrolling on its own (the right pool is `WheelContent#pool`: the active abilities the player holds plus the skills the artifacts in both hands and the Curios slots declare), with one shared row of twelve cells underneath; `Escape` saves and closes. Closing sends a `WheelLayoutC2SPayload` - the **whole layout**, never a per-cell edit - and re-sends the number (the page list was just replaced). **Only the main wheel is edited there**: the pages behind it depend on what is carried, so the editor neither shows nor previews them (the header line says so). Opening it asks nothing of the server - the `/wheel` client command, or the `key.mxt.wheel_configuration` key (unbound by default) - so there is no S2C payload and no round trip for it.
3. **The server validates and stores it**: `WheelService.sanitize` forces the size to twelve, checks per cell that the id resolves in the registry its kind names, normalizes what does not to an empty cell, and writes it back to the attachment. Only the asking player's own attachment is ever written.
4. **Before anything is saved**: what the client reads is **twelve empty cells** - nothing is filled in (the old default fill, first six spirit powers into cells 0-5 and first six abilities into 6-11, has been removed). What sits on the wheel is entirely the player's choice; the price is that with **the whole wheel empty** the wheel does not open on `R` (there is nothing to choose), so a fresh save starts by putting entries on it with `/wheel`.
5. **Resolving into entries**: `WheelContent.entries(player, source)` looks each of a source's entries up in the currently available pool (the main wheel in the available auras and granted abilities, a derived source in the table it just read); an entry that is gone (a revoked grant, a deleted definition, a spirit power the player can no longer pay for) is an **empty cell**, while the saved layout is left alone so it comes back when the grant does. This is the opposite of what the old hotbar did - it backfilled from the runtime list, which let a player's muscle memory drift without them touching anything.

## What a sector draws

Each sector draws its entry's `icon()` on the ring (an item or a texture, 16px); **an entry without one draws its name instead** - `IconRenderer.renderName` takes as much of `title()` as fits and puts it exactly where the icon would have been, so a wheel filled with icon-less entries shows no blank sectors. The label's width is one sector's arc at that radius minus a gap (`WheelMenuScreen#labelWidth`), so two neighbouring names cannot run into each other. The whole name is always in the middle of the wheel and in the tooltip.

The twelve cells of the editor work the same way: an icon if there is one, otherwise the start of the name (`IconRenderer.renderOrName`) - a 22px cell holds two ideographs, and the tooltip has the rest.

## Choosing and using are two keys

`key.mxt.wheel` (`R` by default) **only chooses**: hold it and the pointer picks the sector; letting go (`mode = HOLD`) or pressing it again (`TOGGLE`) **only closes the wheel, and triggers nothing**; **opening always returns to the main wheel**. `key.mxt.wheel_use` (`V` by default, new) **does the using**: while the wheel is up it spends the sector the pointer is on and leaves the wheel standing (so several sectors can be spent in one hold), and while the wheel is down it spends the one **remembered** from last time. A left click is the same as the use key.

**The wheel is current state, and the cell number is the whole of what is remembered** (`WheelSelectionState` holds `page` plus `number`): the ring draws the current page, the HUD grid draws the whole wheel, the twelve slot keys act on the current page, and the use key while the wheel is down acts on whatever cell the number stands for now. Switching is `key.mxt.wheel_previous` / `key.mxt.wheel_next` (**numpad `4` / `6` by default**, rebindable):

- **It works with the wheel up or down**, wrapping at both ends, and every turn says "Wheel 2/3: Main hand" on the action bar - the pages behind the main one depend on what is carried, so once the item is put away those pages are gone and without the line you cannot tell which page you are on.
- **Turning the page leaves the number alone**: a turn is not aiming, so nothing is published either (the number did not change).
- With another screen open (chat, inventory, ...) it does nothing, exactly like the other wheel keys.
- Two more places say which page it is: a line **above** the ring ("Wheel 2/3: Main hand", with the two switch keys named at the end), while the HUD grid writes nothing at all.

- **The current selection is the cell number** (`screen/wheel/WheelSelectionState`'s `number`, `-1` meaning nothing chosen yet): while the wheel is open the pointed cell is written every frame (an empty cell is written as empty - "pointing at nothing is choosing nothing" is more honest than quietly keeping the previous cell), it survives the wheel closing, and `ClientPlayerNetworkEvent.LoggingIn` clears it so the `armed` number the server remembered can be put back (see [Keeping the selection](#keeping-the-selection)). That state also holds **every page as resolved for this client tick** (`pages()`, twelve cells each, `null` for an empty one), because the HUD's grid reads every cell of every page each frame while resolving walks the aura registry and the formulas that decide which auras can burst; it therefore happens once per client tick (the controller refreshes again right after a turn, so the frame and the HUD cannot disagree), so a revoked grant, a deleted definition or a spirit power the player can no longer pay for turns that cell into "no target" within a tick and the use key does nothing.
- **Past the end, the choice falls back to the last skill** (`WheelMenuContent#effective`): when the number **addresses a cell that does not exist** (its page is gone, or that page holds fewer cells than it did), the cell it stands for is **the last one holding anything**; a number that lands inside the existing cells but on an empty one (which only the main wheel has) is still **no target** (the old "pointing at nothing is choosing nothing" rule). **The number itself is never rewritten in any branch**, so when the pages come back the same number points at the same skill again. Aiming at the empty tail of a page read from what you carry does not write the number into cells that do not exist (`selectSector` asks `exists` first): there is no frame to point at there. The gold frame is drawn on what the number stands for now, `V` spends that, and the number that travels is the one that was chosen.
- **These keys and the two switch keys are read raw** (`WheelMenuController` polls `InputConstants`/GLFW) rather than through `KeyMapping`: any `Screen` makes vanilla call `KeyMapping.releaseAll()`, and releasing the wheel key while still holding the use key makes `MouseHandler#grabMouse()` call `KeyMapping.setAll()`, which sets the use mapping down again from the physical key and would present that as a fresh press - one trigger too many. One edge detector per key is what prevents it. With the wheel closed the use key additionally requires that no screen is open, so typing a `v` in chat cannot cast anything.
- **A key that could do nothing says so on the action bar**, in two cases only: the "**the whole wheel is empty**" branch of `open(...)` says "Nothing is on the wheel yet", and `use(...)` reminds you to hold the wheel key and point at a cell when nothing has ever been selected (naming the key you actually bound). **Nothing is said when the selected cell holds nothing usable** (an empty cell, a deleted definition, a revoked grant): the HUD already draws that cell as an empty frame and `V` does not close the wheel, so that branch of `usePointed(...)` stays silent. It goes through the **client** action bar (`Minecraft#gui#setOverlayMessage`) and sends no packet; **with another screen open the keys stay silent** - that is typing in chat or looking through your inventory, not a request.
- **Every one of the twelve slots has a key** (`key.mxt.wheel_slot.1` ... `.12`, **all unbound by default**, in a "**MiXianTu: Wheel Slots**" category of their own): `MxtKeyMappings.WHEEL_SLOTS` is filled by a `for` loop in the static block, index `i` being cell `i` of a page while the number is `i + 1` (the editor numbers the cells from `1` straight up, clockwise). **The order inside the category comes from the key's `order`**: the vanilla key list sorts with `Arrays.sort` → `KeyMapping#compareTo`, which compares `order` first and only falls back to the **translated label**, so without one the list reads `1, 10, 11, 12, 2, ...`; each slot key is given its sector number as that order (`KeyMappingHolder` gained an overload forwarding to the vanilla five-argument constructor), which keeps the numbers unpadded and the order fixed in every language. Pressing a slot key **selects that cell of the current page and spends it right away** (the same as pointing at it and pressing `V`): `useSlotKey(...)` works out the number (`page * 12 + sector`), takes that cell, calls `WheelSelectionState.selectSector(sector)` so the HUD highlight follows and the number persists across sessions, and then `entry.onSelected(...)` sends the trigger; a cell with nothing in it does nothing. **The behaviour lives in `WheelMenuController`'s raw polling rather than in an `onStateChange` callback**: `setAll()` would invent a press, which for a cast means casting something nobody asked for, and raw polling also lets a slot key work while the wheel is open.
- **The `release_to_select` client setting is gone** (letting go no longer picks anything); `mode` (hold / toggle) stays. `WheelSelection.Method` went from `RELEASE`/`CLICK` to `KEY`/`CLICK` and now only says whether the request came from the keyboard or the mouse.
- The middle of the wheel says "Press `V` to use" while the entry can be used (naming whatever key is actually bound) and "On cooldown 4.3s" while it cannot - the remaining time is read from the tick the cooldown ends on (the synced attachment has it) and written by `WheelDuration.seconds` as seconds with **one decimal, always**, the same way the cooldown and cast-time lines in a tooltip are written.
- A movable HUD element, the **Wheel Grid** (`screen/wheel/WheelSelectionEntry`, layout key `wheel.selection`), is **always four columns wide and as many rows as its cells need**, growing downward: it is a view of **the whole wheel**. **Only the main wheel draws empty cells** (those twelve frames are the layout the player arranged), while a page read from what is carried draws only the entries it really contributes - three skills are three cells, with no run of empty frames after them - so a page boundary is no longer necessarily a row boundary. Each cell draws the icon or the start of the name with a strip of the kind's colour along the bottom, washed over while it cannot be used, and an empty cell is just an empty frame. **The cell the chosen number stands for right now is outlined in gold**, the same gold the editor uses for a picked option and the wheel for the pointed cell. Its size is computed from its contents every frame (`layoutWidth` / `layoutHeight` are dynamic and `refreshPlacement` reports the change with `setSize`, so a block that grew past the window is pulled back in), it starts at the **left of the window, halfway down**, and it writes nothing above itself: the ring is what says which page is up. Without it, using the key while the wheel is closed would be a blind cast - and it also shows at a glance what every cell holds.

## Keeping the selection

What the server remembers is **one cell number**, never an entry: cells are numbered straight through the wheel and pages come and go with the gear, so a number is a **place** - it does not expire when its pages do, and when they come back the same number points at the same skill. It lives in the `armed` field of the same `wheel_layout` attachment (`Optional<Integer>`, empty meaning nothing was ever chosen), and `screen/wheel/content/WheelSelectionSync` owns both directions:

- **Restoring, once per login**: the client reads the synced attachment and writes the number into `WheelSelectionState` (`restore`) - it resolves nothing, checks nothing and warns about nothing, because "this place holds nothing at the moment" is a legitimate state; what the number stands for is worked out by the [fallback rule](#choosing-and-using-are-two-keys). The attachment is sent after the player joins, and "not here yet" looks exactly like "this player has never chosen anything" for the first ticks, which is why the attachment is consulted each tick until it arrives; once the session has a choice of its own it is never consulted again.
- **Publishing, on change only**: a `WheelSelectionC2SPayload` (`Optional<Integer>`) goes out when the number changes - not while the wheel is down, not when a page is turned, and not while the pointer stays inside one cell. Saving a layout **re-sends it by force**, because the page list was just replaced.
- **The server only checks the range**: `WheelService.sanitizeArmed` accepts `0..MAX_ARMED` and treats anything else as "nothing chosen", resolving nothing and warning about nothing - it cannot tell whether that cell holds anything, and should not try (that depends on what the player is carrying). The attachment syncs to its owner, so what the client restores from is the number the server accepted.

## Triggering

There is exactly one channel: `WheelActionC2SPayload(source, kind, id)` - which source, which kind, which id, resolved by the client from **the cell it stood on at that moment**. `WheelService.trigger` first demands that **the named source still holds the entry** (`WheelSources#offers`: the saved layout for the main wheel, the current grants for the abilities of a derived source, the stacks that page reads for its artifact skills) and drops the whole request when it does not, and only then dispatches:

- `ABILITY` → `AbilityService.use`, which re-checks the grant, the conditions, the costs, the cooldown and the cast time;
- `AURA` → `SpiritBurstService.fireOnce`, which re-checks the element, the use condition, the cooldown and the stored value before firing one `SpiritBurstEntity`;
- `ARTIFACT` → `ArtifactToggleService`: re-read the cell off the page the request named and call the implementation's own `activate(...)` (a switch reads its state and picks a side; the storage opens its box). A refusal is logged and reported on the action bar as "Use failed: reason" (`actionbar.mxt.artifact_skill.*`).

**The main wheel goes through that check too**: the layout is submitted by the client anyway, so this is not an anti-cheat measure but what makes "this entry really comes from the source you named" true of every source - clear a cell in the editor while still holding `V` and that request is refused. **The number plays no part in a trigger**: it only answers "which cell".

**There is no cancel.** Using triggers once, so there is no release gesture left to cancel a pending cast or stop a burst with - letting go of the wheel key only closes the wheel - and a channelled ability can no longer be interrupted by its caster.

On the data-pack side, the `slot` field of `mxt:active` is **no longer read** - where an entry sits is the player's twelve-cell layout now - and writing it neither errors nor does anything.
